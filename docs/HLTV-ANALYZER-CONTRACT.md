# External HLTV analyzer adapter contract v1

`api/src/hltv/analyzer.js` defines `analyze(input)` and `validateResult(input, output)`. `UnavailableAnalyzer` returns `unsupported` with **no findings**. Registry imports use `unsupported` until the real integration is enabled. There is no module auto-loader, parser executable, detector algorithm, fake confidence, or production analysis scheduler in this release. The schema reserves analysis runs/anomalies for the future worker. Do not flip a setting and assume analysis is running.

The future isolated worker must pass the existing local immutable demo to an adapter, never download it again. It must validate SHA-256 first, enforce CPU/RAM/timeout/output bounds and an abort/kill mechanism for its subprocess, and persist results transactionally. A JS timeout alone does not stop a parser process. The web process and Discord delivery must not execute that parser.

## Input

```json
{
  "contract_version": 1,
  "analysis_run_id": "registry-generated-uuid",
  "demo_id": "registry-generated-uuid",
  "match_id": "existing-canonical-match-id",
  "round_id": null,
  "server": "east",
  "map": "2fort",
  "recorded_at": 1794690000000,
  "local_path": "/srv/noname-hltv/incoming/uuid/round.dem",
  "sha256": "64 lowercase hexadecimal characters",
  "size_bytes": 12345678,
  "players": []
}
```

`local_path` is generated by trusted storage resolution and passed only to the isolated adapter. It is never a browser-provided path or URL. `round_id` and player identities remain unknown unless verified from canonical data/parser output. `players`, when known, contain canonical `player_steam_id` and optional Discord ID/display name. Input timestamps use epoch **milliseconds**; demo-relative `time_seconds` uses seconds. The analyzer must report ticks in the original demo tick coordinate system and document tick rate/time mapping and any HLTV limitations.

## Output

```json
{
  "contract_version": 1,
  "demo_id": "same-input-demo-id",
  "sha256": "same-input-checksum",
  "status": "complete",
  "parser_version": "real-parser-release-or-commit",
  "detector_version": "real-rules-release-or-commit",
  "anomalies": []
}
```

Only `complete` means a successful analysis. `failed` and `unsupported` must contain an empty anomalies array and an error/reason. They preserve raw data. `complete` with an empty array means the real configured analyzer finished and found nothing under its documented supported detectors; it is never a fallback for a timeout or unsupported data.

An anomaly object must have:

| Field | Contract |
|---|---|
| `event_id` | Stable nonempty event key unique within a run; deduplicate repeated events/rules before persistence |
| `type` | Actual supported anomaly type/category; no detector types are promised by this release |
| `rule_id`, `rule_version` | Reproducible real detector identity/version |
| `severity` | `info`, `low`, `medium`, `high`; review priority, never an automatic conviction |
| `start_tick`, `end_tick` | Nonnegative integer or null; end requires start and cannot precede it |
| `time_seconds` | Nonnegative demo-relative time or null; at least a start tick or time is required |
| `player_steam_id` | Canonical SteamID or null; never guess an identity |
| `confidence` | Null if uncalibrated, otherwise 0..1 with nonempty `confidence_basis`; not probability of cheating |
| `confidence_basis` | Validation/calibration explanation or null when confidence is unknown |
| `summary` | Concise human-readable explanation with limitations |
| `evidence` | Structured JSON object: measured facts, expected values, relevant events/ticks, parser capability/uncertainty; no arbitrary filesystem or external URL fetches |

Optional scores are heuristic measurements and must be explicitly named/described within evidence. No automatic penalties, bans or ELO changes are allowed. Supporting assets/files need separately registered, authenticated storage before links can be rendered. The current UI uses textContent; it never executes analyzer HTML or renders arbitrary evidence URLs.

`validateResult` enforces identity/checksum/status, required fields, unique event IDs, valid tick/time/confidence ranges, maximum 10,000 events and 1 MiB serialized result. The eventual process transport must enforce byte limits **before** deserializing output; post-parse validation alone is not a resource limit. Capability reports and player identity validation must be added alongside the real parser after inspecting its actual output.

## Future worker integration acceptance checklist

1. Add opt-in analyzer configuration, a durable DB job claim/lease/retry/dead-letter scheduler, and a real isolated adapter. No adapter means unsupported, not success. Recover processing leases as failed/retryable after crashes.
2. Create a run with parser/detector versions and processing state. Hold/incomplete state blocks cleanup. Supply original local path and verified identity; bound concurrency and process resources.
3. Validate output before writes. Insert `hltv_analysis_runs` and `hltv_anomalies` in one IMMEDIATE transaction; include input hash, exact versions, timestamps, run ID and reproducible evidence. Do not accept stale results if the claimed recording/run changed.
4. Queue medium/high real findings for human review, extend expiration without shortening existing retention, create explicit holds and a durable `analyzer_finding` outbox event. Preserve existing admin/report holds and evidence regardless of rescore. Deduplicate events across retries/runs; do not spam alerts for equivalent results.
5. Failures/timeouts/unsupported retain bytes and expose errors for admins; never set complete from an exception path. Reanalysis must clear any prior manual waiver before starting so incomplete new analysis cannot be cleaned under an old waiver.
6. Test with real TFC HLTV samples, known false positives, parser crashes, corrupt recordings and incomplete capabilities. Validate the parser's own license/endpoints and asset rights before a separate authenticated browser viewer integration.

Automated detector implementation, worker execution integration, result ingestion and playback are **pending the external parser**. Manual review, storage, holds, cleanup and alert infrastructure operate without it.
